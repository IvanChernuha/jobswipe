4. NOTIFICATIONS — DESIGN (approved direction, build next)
==================================================================
Types (each individually on/off per user; defaults ON):
  - match         both sides       "It's a match with Demo Tech Inc"
  - like_received employers only   "3 new candidates liked your Frontend job"
                  (HOLD for workers: revealing who liked you changes the mutual-match dynamic — user to decide)
  - chat          both             "New message from Alice"
  - team          org members      "Dana posted 'Junior QA'", "Yossi matched with a candidate", "Noa replied"
                  Rules: never notify a member about their OWN action; only for things their role can see
                  (Viewer gets no chat notifications). Org/role system already defines team + permissions.
  - account/jobs  "Your job expires in 3 days", "CV analyzed — 5 skills added"
Data:
  - notifications(id, user_id, type, title, body, link, created_at, read_at)  [+ index user_id, read_at]
  - notification_prefs(user_id, type, enabled)  (or one row with a JSON/bool per type)
  - Emit from existing event sites: swipes (match), messages (send), employers (job create/edit),
    cv_processing (done/error), job-expiry cron.
  - Delivery channels as a 2nd axis later: in-app (now) → email digest (Resend) → push (PWA/Android).
    Same table feeds all three.
UI:
  - Bell in Navbar with unread count (extend the existing 30s poll), dropdown/page list, "mark all read".
  - Preferences = toggles on Profile page. Both languages (add keys to en.json + he.json).
Size: ~1 session (backend + frontend + tests + i18n). Migration = supabase/migrations/012_notifications.sql
(additive; apply with `docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 < file`).

5. HOW TO WORK (conventions that saved time)
==================================================================
- Verify before commit: `docker build ./backend` + pytest inside the image (see memory "Local verification
  recipe"); `docker build ./frontend` = tsc + vite; then `docker compose up -d --build <svc>` to deploy locally;
  browser checks via a Playwright subagent (scripts in the session scratchpad get lost — it re-creates them).
- Push to main = GitHub Actions → GKE deploy (prod reachability unknown; ingress has placeholder domain;
  frontend build now expects /supabase on its own origin — GKE would need that route or VITE_SUPABASE_URL).
- Use `[skip ci]` for docs/scripts-only commits.
- Fable budget: use Sonnet (/model claude-sonnet-5) for mechanical work (P3, string extraction);
  keep Fable/Opus for design decisions.
- Migrations are hand-written SQL in supabase/migrations/, applied manually. Do NOT run alembic autogenerate.
- Backup: scripts/backup_db.sh (cron installed but commented out until release); scripts/restore_drill.sh.
